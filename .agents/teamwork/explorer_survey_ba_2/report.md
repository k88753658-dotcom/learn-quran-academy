## 1. Executive Summary

The Learn Quran Academy application is migrating its authentication layer from Clerk (`@clerk/nextjs`) to the open-source **Better Auth** library with the **Prisma adapter** running against a Neon PostgreSQL database.

Under Clerk, user identities were tracked using the Clerk user ID (e.g. `user_2b...`) stored directly in `Profile.id`. The entire codebase (over 59 queries across 25+ API routes and pages) was built around this contract: `Profile.id` IS the authenticated user's ID.

### Key Finding & Strategy Recommendation
Rather than breaking existing domain relations or merging all profile data into Better Auth's internal authentication table, the application should implement a **Shared Primary Key 1:1 relation** between Better Auth's `User` model and the existing `Profile` model:
- `User.id` (String primary key generated by Better Auth / cuid)
- `Profile.id` (String primary key referencing `User.id` with `onDelete: Cascade`)
- `Profile` retains all academy-specific fields (`role`, `whatsapp`, `bio`, `specializations`, `qualification`, `experienceYears`, `isProfileComplete`, etc.).
- All existing domain relations (`Student.profileId`, `Student.teacherId`, `Attendance.markedById`) remain completely untouched and valid.
- Every existing query using `prisma.profile.findUnique({ where: { id: userId } })` continues to work seamlessly because `userId` resolved from `auth.api.getSession()` is `session.user.id == profile.id`.

## 3. Better Auth Prisma Adapter Requirements

Better Auth requires four core models when using its database adapter:
1. `User` — Core user identity.
2. `Session` — Active user sessions and tokens.
3. `Account` — Authentication accounts and credentials (where email/password hashes and OAuth links are stored).
4. `Verification` — Email verification and password reset tokens.

### Detailed Model Specifications

```prisma
model User {
  id            String    @id @default(cuid())
  name          String
  email         String    @unique
  emailVerified Boolean   @default(false) @map("email_verified")
  image         String?
  createdAt     DateTime  @default(now()) @map("created_at")
  updatedAt     DateTime  @default(now()) @updatedAt @map("updated_at")
  role          String?   @default("student")

  sessions      Session[]
  accounts      Account[]
  profile       Profile?

  @@map("user")
}

model Session {
  id        String   @id @default(cuid())
  expiresAt DateTime @map("expires_at")
  token     String   @unique
  createdAt DateTime @default(now()) @map("created_at")
  updatedAt DateTime @default(now()) @updatedAt @map("updated_at")
  ipAddress String?  @map("ip_address")
  userAgent String?  @map("user_agent")
  userId    String   @map("user_id")
  user      User     @relation(fields: [userId], references: [id], onDelete: Cascade)

  @@index([userId])
  @@map("session")
}

model Account {
  id                    String    @id @default(cuid())
  accountId             String    @map("account_id")
  providerId            String    @map("provider_id")
  userId                String    @map("user_id")
  user                  User      @relation(fields: [userId], references: [id], onDelete: Cascade)
  accessToken           String?   @map("access_token")
  refreshToken          String?   @map("refresh_token")
  idToken               String?   @map("id_token")
  accessTokenExpiresAt  DateTime? @map("access_token_expires_at")
  refreshTokenExpiresAt DateTime? @map("refresh_token_expires_at")
  scope                 String?
  password              String?
  createdAt             DateTime  @default(now()) @map("created_at")
  updatedAt             DateTime  @default(now()) @updatedAt @map("updated_at")

  @@index([userId])
  @@map("account")
}

model Verification {
  id         String    @id @default(cuid())
  identifier String
  value      String
  expiresAt  DateTime  @map("expires_at")
  createdAt  DateTime? @default(now()) @map("created_at")
  updatedAt  DateTime? @default(now()) @updatedAt @map("updated_at")

  @@map("verification")
}
```

### Critical Adapter Mechanics
1. **Password Storage**: In Better Auth with `emailAndPassword: { enabled: true }`, hashed passwords are stored in the `Account` model where `providerId = "credential"`, `accountId = user.id`, and `userId = user.id`. The password is never stored on the `User` model.
2. **Session Verification**: The `Session` model stores the active `token` and `expiresAt` timestamp. When Better Auth validates a request, it queries `Session` using the token extracted from the request cookies (`better-auth.session_token`).
3. **Table & Column Naming**: Prisma Client exposes properties in camelCase (`createdAt`, `expiresAt`, `userId`), which Better Auth's adapter queries directly through `prisma.user`, `prisma.session`, `prisma.account`, and `prisma.verification`. Prisma handles the `@map("snake_case")` column mapping and `@@map("table_name")` mapping internally.

## 4. Integration Strategy: Better Auth `User` vs Existing `Profile`

### Comparison of Architectural Options

| Approach | Description | Pros | Cons | Verdict |
|---|---|---|---|---|
| **Option A: Shared Primary Key (Recommended)** | `Profile.id` is both PK and FK referencing `User.id` (`onDelete: Cascade`). | 1. Zero breaking changes to all 59+ existing queries. 2. `Profile.id === User.id === session.user.id`. 3. Foreign keys (`Student.profileId`, `Student.teacherId`, `Attendance.markedById`) remain completely unchanged. 4. Deleting a `User` cascades to delete `Profile`. | None. Standard Prisma 1:1 table extension pattern. | **ACCEPTED** |
| **Option B: Independent UUID with `userId` FK** | `Profile` gets its own `id UUID`, and adds `userId String @unique` referencing `User.id`. | Separate ID space. | Breaks every existing query using `prisma.profile.findUnique({ where: { id: userId } })`, and requires migrating `Student.profileId`, `Attendance.markedById`, etc. | REJECTED |
| **Option C: Merge `Profile` into `User`** | Delete `model Profile` entirely and move all 11 profile columns into `model User`. | Single user table. | Violates separation of concerns. Requires rewriting all 59+ `prisma.profile.*` references and renaming relation fields across all components and API routes. | REJECTED |

### The Updated `Profile` Model

```prisma
/// User profile synchronized with Better Auth User
model Profile {
  id                 String    @id // Synchronized with User.id
  user               User      @relation(fields: [id], references: [id], onDelete: Cascade)
  name               String
  email              String    @unique
  role               UserRole  @default(student)
  whatsapp           String?
  bio                String?
  specializations    String[]  @default([])
  qualification      String?
  experienceYears    Int?      @default(0) @map("experience_years")
  isProfileComplete  Boolean   @default(false) @map("is_profile_complete")
  profilePhotoUrl    String?   @map("profile_photo_url")
  lastActive         DateTime? @map("last_active")
  createdAt          DateTime  @default(now()) @map("created_at")
  updatedAt          DateTime  @default(now()) @updatedAt @map("updated_at")

  // Relations
  studentProfile     Student?     @relation("StudentProfile")
  teacherStudents    Student[]    @relation("TeacherStudents")
  markedAttendances  Attendance[] @relation("MarkedAttendances")

  @@map("profiles")
}
```

### Role Synchronization Strategy
1. **In Better Auth**: Configured via `user.additionalFields` with `role: { type: "string", defaultValue: "student" }`. This ensures `session.user.role` is populated immediately upon session retrieval for fast middleware and client-side authorization.
2. **In Prisma `Profile`**: Keeps the strongly-typed `UserRole` enum (`student`, `teacher`, `admin`) for full type-safety and backward compatibility with domain logic.
3. **During User Creation**: When registering a user or creating a teacher/student via API routes:
   - Better Auth creates the `User` and `Account` records (e.g. via `auth.api.signUpEmail`).
   - The application creates the `Profile` with `id: user.id` and `role: "student" | "teacher" | "admin"`.

### Phase 4: Better Auth Server & Client Modules Setup
1. **Server Configuration (`src/lib/auth.ts`)**:
   ```typescript
   import { betterAuth } from "better-auth";
   import { prismaAdapter } from "better-auth/adapters/prisma";
   import { prisma } from "@/lib/prisma";

   export const auth = betterAuth({
     database: prismaAdapter(prisma, {
       provider: "postgresql",
     }),
     emailAndPassword: {
       enabled: true,
       autoSignIn: true,
     },
     user: {
       additionalFields: {
         role: {
           type: "string",
           required: false,
           defaultValue: "student",
           input: true,
         },
       },
     },
   });
   ```

2. **Client Configuration (`src/lib/auth-client.ts`)**:
   ```typescript
   import { createAuthClient } from "better-auth/react";

   export const authClient = createAuthClient({
     baseURL: process.env.NEXT_PUBLIC_BASE_URL || "http://localhost:3000",
   });

   export const { signIn, signOut, signUp, useSession } = authClient;
   ```

3. **API Route Catch-All Handler (`src/app/api/auth/[...all]/route.ts`)**:
   ```typescript
   import { auth } from "@/lib/auth";
   import { toNextJsHandler } from "better-auth/next-js";

   export const { POST, GET } = toNextJsHandler(auth);
   ```

### Phase 5: Downstream Code Migration Guide (For Subsequent Milestones)
1. **API Route Server Session Verification**:
   Replace:
   ```typescript
   import { auth } from "@clerk/nextjs/server";
   const { userId } = await auth();
   ```
   With:
   ```typescript
   import { auth } from "@/lib/auth";
   import { headers } from "next/headers";
   const session = await auth.api.getSession({
     headers: await headers(),
   });
   const userId = session?.user?.id;
   ```
2. **Programmatic User Creation in Admin Routes (`add-teacher`, `add-student`, `approve-teacher-application`)**:
   Replace `clerkClient().users.createUser(...)` with `auth.api.signUpEmail({ body: { email, password, name, role } })`.
3. **Middleware**:
   Replace `@clerk/nextjs/server`'s `clerkMiddleware` with a lightweight session cookie check using `getSessionCookie` from `better-auth/cookies` or standard Next.js cookie inspection.
4. **Root Layout & UI**:
   Remove `<ClerkProvider>` from `src/app/layout.tsx`. Build custom Tailwind Login and Register forms using `authClient.signIn.email` and `authClient.signUp.email`. Update Navbar using `authClient.useSession()` and `authClient.signOut()`.
